# @minions/session-context

Live, per-session pointer to the current wing root / work root, plus the path-resolution and Bash-preamble logic that hangs off it.

## Why this is a separate package from `@minions/file-store`

`@minions/file-store` represents **what is actually on disk** — `Lair`, `Wing`, `Directory`, junctions, worktrees — queried on demand, with no notion of "the current session" or any mutable, in-process pointer. `Wing` already models `workLocal()`/`workNamed(name)` etc. as things you can *ask about*, not a live cursor into "the one the current agent is using right now."

This package's job is different in kind: it tracks **which work root a specific running session is currently pointed at**, a piece of runtime/session state that has no disk-representation analog and doesn't fit file-store's domain (disk structure) without stretching it to also mean "process-local session state," which is a different axis entirely (per this wing's CLAUDE.md: "each domain owns its infrastructure... technical domains are discovered, not planned"). It depends on `@minions/file-store`-shaped concepts (wing root, work root) but does not depend on the package itself — the coupling is conceptual, not code-level, since this package doesn't need the full disk-model API to do path arithmetic on strings.

**Trade-off worth flagging, not hidden:** this is a close call, not a slam dunk. An alternative reading is that "which work root is active" is just another fact about a `Wing` instance and belongs as a method on `Wing` (e.g. `wing.currentWorkRoot(sessionId)`), keeping one package instead of two. The reason I didn't go that way: `file-store`'s `Wing`/`Lair` objects are constructed per-call from disk state (no persistent identity across process boundaries), while session state needs to persist *across* the many short-lived hook-script processes a single Claude Code session spawns (one per tool call) — that's an architectural mismatch with file-store's current object-per-call-site shape, not just a missing method. If file-store's object model changes to support long-lived instances, this call is worth revisiting.

## What's here

- `pathResolution.mjs` — the 3-branch path-resolution rule (wing-root-relative / absolute / work-root-relative), used by the structured-tool `PreToolUse` hook.
- `workRootState.mjs` — per-session work-root state, persisted to `<wingRoot>/private/untracked/session-context/<sessionId>.json`.
- `bashEnv.mjs` — builds the `$WING_ROOT`/`$WORK_ROOT` export + `cd` preamble prefixed onto every Bash command.
- `wingRoot.mjs` — resolves wing root from a hook script's fixed on-disk location relative to wing root, no marker-file scanning needed.

Correction happens entirely at `PreToolUse` time, before a bad path ever reaches the tool: a wrong `file_path`/`path` is caught and fixed by `denying` the call with a `permissionDecisionReason` that hands the model the corrected path to retry with (see point 2 below). There is no separate `PostToolUseFailure`-based correction step, because one couldn't work in this harness even if built — those hooks don't support `additionalContext` at all here (only `decision: block`/`reason`/`systemMessage`), so they have no channel to hand the model a corrected path after the fact. Catching the problem pre-execution, where the harness actually gives a hook a way to redirect the call, is the only mechanism that fits.

## How path resolution actually works (verified against live harness behavior, not just via stdin replay)

Two harness behaviors, undocumented and only discoverable by driving real tool calls, shape how `pathResolution.mjs` and `.claude/hooks/path-resolve.mjs` work:

1. **The harness pre-resolves a bare relative `file_path`/`path` to an absolute path against wing root** (not work root) before any `PreToolUse` hook sees it. So `Read("sharing-keystones/x")` arrives at the hook as `file_path="<wingRoot>/sharing-keystones/x"` — already absolute. The naive "absolute → assume correct" branch of the 3-branch rule is therefore wrong for this harness; `resolvePathForTool()` re-roots absolute-under-wingRoot-but-not-a-wing-root-sibling paths under `workRoot` instead of trusting them as-is.
2. **`hookSpecificOutput.updatedInput` is honored for `Glob`'s `pattern` field but NOT for `file_path` (Read/Write/Edit) or `path` (Glob/Grep)** — confirmed by feeding the hook a correctly-resolved `file_path` via `updatedInput` and observing the tool still used the original wrong path. For those fields, the hook instead `deny`s with `permissionDecisionReason`, which IS honored — it blocks the call and tells the model the corrected path to retry with. Visible-and-effective, not silent.
3. **The absolute-path branch checks the wing-root-relative leading segment against `WING_ROOT_SIBLINGS` before falling back to an existence check**, mirroring what the relative-path branch already does. This is why a brand-new file under a real sibling (e.g. `<wingRoot>/work/minions/...`) is trusted unconditionally instead of being misdiagnosed as the harness's pre-resolution behavior just because it doesn't exist yet — the existence check only runs as a fallback for genuinely ambiguous non-sibling top-level paths, e.g. the wing's own top-level `CLAUDE.md`, or an incidental file that happens to sit at wing root (a scratch script, a leftover screenshot). Covered by a regression test.

## Known gaps (real, not hidden)

1. **Sub-agent work-root inheritance is not implemented.** The observed `PreToolUse`/`SessionStart` hook stdin contract exposes `session_id` but no parent-session link, so a sub-agent's session-context state cannot be seeded from its parent's *current* work root if that root was ever changed mid-session — it falls back to the same default (`work/local`) as any fresh session. Only the *default* is guaranteed consistent across a session tree. Fixing this needs either a harness-level parent-session-id field in hook stdin, or an explicit hand-off mechanism the parent writes before spawning — neither exists today.
2. **`Glob`'s `path` param and `Grep`'s `path` param cannot be corrected at all.** When the raw relative path doesn't resolve to a real directory under wing root, those tools fail with their own "does not exist" error WITHOUT ever invoking `PreToolUse` hooks — confirmed live via file-based logging showing zero hook invocations for these failing calls. There is no interception point before the failure; no hook mechanism can fix this in the current harness version. Workaround: prefer folding the target directory into `Glob`'s `pattern` (e.g. `"sharing-keystones/**/*.md"` instead of `pattern: "*.md", path: "sharing-keystones"`), and avoid passing `path` to `Grep` — pass the directory as part of a broader search instead.
3. **Mid-script Bash navigation** (a `cd` after the first command in a `&&` chain, or a path inside e.g. a `git -C <path>` argument) is not rewritten — only the shell's *starting* directory is fixed. This is a deliberate scope boundary (see the original design discussion: safely rewriting arbitrary shell command text was rejected as unsafe), not an oversight.
4. **`WING_ROOT_SIBLINGS` is a hardcoded allowlist, not discovered from disk.** It's kept in sync manually against the actual stable DIRECTORY entries at wing root (`work`, `private`, `info`, `closet`, `.claude`, `.mcp.json`, `.playwright` — verified against both tooling-01 and tooling-00). `CLAUDE.md` is deliberately NOT in this list even though it's a stable wing-root entry too — see the note in `pathResolution.mjs` on why (work/local has its own CLAUDE.md, and a bare relative "CLAUDE.md" is meant to mean that one). A future wing that adds a new stable top-level *directory* would need this list updated by hand. A `fs.readdirSync(wingRoot)`-based dynamic version was considered but not built — out of scope for this pass, worth reconsidering if the list needs to change often.
