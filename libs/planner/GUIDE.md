# Planner — Implementation Guide

## What it is

A Mikado-method planning system. Plans are trees of work items. Items exist only while work remains — completing an item means deleting it. The tree converges to empty as work is done.

Plans are stored as files in the same git repo as the code they describe, committed alongside code changes. This means plan history is code history.

## Data model

See `@minions/planner-types`'s `src/types.ts` for the authoritative definitions. In brief:

```
ItemType = 'task' | 'fork' | 'option'

PlanItem {
  id: string          // 8-char hex, e.g. "a1b2c3d4"
  title: string
  type: ItemType
  parent: string | null
  children: string[]
  requires: string[]  // partial order: must complete these before this
  exploring?: Record<string, string>  // fork only: optionId → branchName
}

SubtreeIndex {
  root: string
  items: Record<string, PlanItem>  // all items including root
}
```

Children are parallelizable by default. `requires` imposes ordering within a subtree.

## File layout

```
plans/planner/
  {rootId}/
    index.json     ← SubtreeIndex; authoritative for all structure
    {itemId}.md    ← pure markdown content; one file per item in subtree
```

`index.json` is the single source of truth. `.md` files are content-only — no frontmatter, no structural data. Create a `{itemId}.md` file (even empty) whenever a new item is added to the index.

## Core invariants

- **deleteItem** removes the item and all its descendants. It also sweeps every surviving item in the subtree and removes the deleted IDs from their `requires` lists.
- **index.json** is always written atomically (full rewrite). Never partially update it.
- **IDs** are generated by `generateId()` (in `@minions/planner-types`) — 4 random bytes, hex-encoded. Never derive IDs from content.
- Each top-level item has its own directory. Different roots never conflict in git.

## Forks

A `fork` item represents a decision point. Its direct children are all `option` type. The fork lifecycle:

1. **Create**: `addChild(parentId, 'Fork title', 'fork')`, then add option children with type `'option'`.
2. **Activate**: Create one git branch per option, named `possibly-wrong/{forkId}/{optionId}`. Call `setExploring(forkId, { optionId: branchName, ... })`. Work on each option branch independently.
3. **Resolve**: Choose a winning option. Merge its branch. Call `clearExploring(forkId)`. Delete the losing option branches (and their plan items).
4. **Common prefix detection**: If commits appear on all option branches before any divergence, that work can be moved before the fork. Surface this as a hint to the user.

Branch naming is strictly `possibly-wrong/{forkId}/{optionId}` — the prefix marks these branches as expendable.

## MCP tool

Exposed via `handlePlanTool(store, args)` in `src/PlanTool.ts`. Dispatches on `args.action`:

| action | required args | what it does |
|---|---|---|
| `list-roots` | — | returns `[{ id, title }]` for all roots |
| `get-subtree` | `itemId` | finds item anywhere in the forest; returns `SubtreeIndex` of item + descendants, plus `details` and `parentContext` markdown |
| `delete-subtree` | `itemId` | ⚠️ dangerous — calls `deleteItem(itemId)`, removing the item and its whole subtree |
| `add-children` | `parentId`, `children: [{title, type?}]` | adds sub-items, returns created `PlanItem[]` |

The cabinet registers this on `/mcp/henchery` and `/mcp/conductor` when `FF().PLANNING_TOOL` is true. The store is `WorktreePlanStore` pointed at `plans/planner/` relative to `work/local`.

## Adapters

- `InMemoryPlanStore` — in-memory, for tests.
- `WorktreePlanStore` — file-backed, accepts `Worktree | Directory` from `@minions/file-store`.

Both must pass all tests in `@minions/planner-types`'s `src/contracts.ts` (`runPlanStoreContractTests`). Add new contract tests there before implementing new behavior.

## Public API

`createInMemoryPlanStore()` / `createWorktreePlanStore(planDir)` — factory functions, both typed to return `IPlanStore`. The concrete `InMemoryPlanStore`/`WorktreePlanStore` classes are internal; consumers only ever see the interface.
